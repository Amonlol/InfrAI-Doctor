# Security policies and network benchmark

## Description
The main focus of this benchmark is the `FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED` environment variable and how it affects the network security layer.
In the [floci description](https://github.com/floci-io/floci/blob/main/README.md#security-group-enforcement) it is stated:
> By default, security groups on EC2 instances and ECS awsvpc ... do not filter traffic. With FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED=true, Floci gives each Docker-backed instance and awsvpc task its own network namespace with an nftables default-deny policy, and filters new connections between Floci-managed containers by the sender's egress rules and the receiver's ingress rules, matched against the ENIs' own IPv4 and IPv6 addresses and group memberships. Replies to an allowed connection pass through connection tracking. It does not emulate VPC routing, network ACLs, NAT gateways or peering.

Therefore, establishing a verified baseline of these network enforcement rules is a mandatory step before expanding the core scope of this project

## Benchmark structure

* ec2.tf - EC2 instances
* network.tf - VPC, subnet, security group
* outputs.tf - outputs EC2 and RDS ids
* provider.tf - AWS provider manifest
* rds.tf - RDS instance
* terraform.tf - Terraform manifest
* test.sh - all-in-one script (terraform deploy + connection testing)

## Testing method

By default, `FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED` is set to `false`. The validation strategy begins by executing connectivity checks with `no_ingress_rules`, then toggling the variable to `true` and repeating the same tests. Finally, one additional test run is required with the `allow_all` rule to ensure that traffic flows as expected when the security group is opened.

1. Create a VPC, subnet, and security group without an ingress rule
2. Attach resources to the security group
3. Check connectivity from the attacker EC2 instance to the listener EC2 and RDS

Testing is conducted using EC2 and RDS for both `FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED` settings to verify the behavior described in the documentation. RDS was selected because it is omitted from the official documentation, however, any other resource could be used.

## FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED set to `false`

### Expected results

The attacker EC2 instance can communicate with the EC2 listener and RDS

### Actual results

Script output:

## FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED set to `true`

### Expected results

The attacker EC2 instance can NOT communicate with the EC2 listener, but can communicate with RDS

### Actual results

Script output:
```shell
FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED is set to true

🔍 Testing connection to EC2 listener server at 172.19.0.5:8080
🔴 Connection failed!

🔍 Testing connection to RDS instance at 172.19.0.2:7001
🟢 Connection is successful!
```

When testing with the `allow_all` security group, we see correct connectivity and results for the listener server as expected:

```shell
FLOCI_NETWORK_SECURITY_GROUP_ENFORCEMENT_ENABLED is set to true

🔍 Testing connection to EC2 listener server at 172.19.0.5:8080
🟢 Connection is successful!
```

## Summary

The benchmark experiments confirmed the exact structural boundaries of Floci's network isolation:

1. In **default mode (`false`)**, security groups function merely as configuration metadata at the AWS API management plane level, allowing all data-plane traffic to flow freely across the shared Docker network mesh without any packet filtering.
2. In **enforcement mode (`true`)**, strict `nftables` isolation is successfully applied to compute layers such as EC2 instances and ECS awsvpc tasks, meaning connections are dropped unless explicit Ingress/Egress rules are defined.
3. Managed data services like RDS **entirely bypass** the `nftables` network namespace sandboxing engine, leaving direct container-to-container connections to the database inherently exposed regardless of the environment variable configuration.

### 🧠 Architectural Takeaway for InfrAI-Doctor
Because local emulators only partially replicate AWS network boundaries and are highly dependent on localized host runtime behaviors, runtime connectivity smoke tests cannot serve as a reliable deployment gatekeeper. Relying single-handedly on automated testing environments to catch networking regressions leaves a critical security blind spot.

To safely validate infrastructure code generated by autonomous AI agents, InfrAI-Doctor enforces a strict two-layer validation strategy:

* **Layer 1** executes deterministic reachability and compliance checks directly against the static Terraform plan JSON using Open Policy Agent (OPA/Conftest) before any resource hits the sandbox.
* **Layer 2** utilizes the local Floci sandbox strictly as a behavioral environment to evaluate clean application booting, user data script execution, and functional service interoperability.
